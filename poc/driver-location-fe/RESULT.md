# P0-9 PoC 结论（前端部分）

日期：2026-10-23  
执行：FrontendSenior  
范围：仅前端最小页面与本地 mock；不涉及后端、存储、真实服务、Telegram Bot 或真机。

## 结论

**建议暂不提前启动司机 App。**

前端侧的关键路径已经被证明：固定间隔采集、离线持久化、恢复后全量补传、幂等去重都能工作。但决定司机 App 是否要提前排期的三个产品风险仍未被验证：真机定位精度与权限、后台/锁屏时的定位存活、耗电。这三项无法用浏览器模拟替代，需要真机 + 测试 Bot + 真实后端接口。因此当前证据足以支撑“继续做前端骨架”，不足以支撑“提前启动司机 App 的完整开发与投放”。

建议下一步：拿到测试 Bot 与真机后，先做一次小范围真机验证（前台 10 分钟、切后台 5 分钟、锁屏 5 分钟、记录耗电与定位间隔），再回来拍板。

| 项 | 结果 | 证据 |

| 同一幂等键重复投递只记一次 | 通过（第一次 accepted，第二次 duplicate，最终 1 条） | `evidence/02-core-tests.txt` |

说明：AC-1/AC-2 的浏览器实测使用 `fakeLocation=1`，验证的是“采集 → 队列 → 上报 → 持久化 → 补传”的代码路径，不是 GPS 硬件表现。

## 前端限制与未验证项

| # | 限制 / 未验证项 | 影响与建议 |
| --- | --- | --- |
| 1 | 真机定位精度、权限弹窗、室内漂移 | 未验证；需真机与真实 GPS，浏览器模拟不能代表 |
| 2 | 后台/锁屏定位 | 未验证；`setInterval` 在后台会被节流或挂起，可能需要原生后台任务或持续定位方案 |
| 3 | 耗电 | 未测；高精度 + 高频采样的耗电必须真机测量后再定间隔 |
| 4 | `navigator.onLine` 不可靠 | 实测 mock 与 preview 全部停止时它仍可能为 `true`；不能作为唯一在线判据，应以请求失败为准（当前实现已按失败保留） |
| 5 | localStorage 容量、可被清理、未加密 | 仅适合 PoC；生产建议 IndexedDB + 加密 + 明确的保留/清理策略 |
| 6 | 队列上限 1000 条 | 超出丢弃最旧点；长时间离线会丢数据，上限需业务确认 |
| 7 | 无退避、无批量上传、无服务端 ACK | 当前逐条 POST，失败即停止本轮；生产需要退避、批量与服务端确认语义 |
| 8 | Service Worker 更新 | `skipWaiting` 会立即切换新版本，缺少“有新版本”提示与刷新引导 |
| 9 | 高棉语文案 | 三语已齐，但高棉语为草案，需业务/母语审校 |
| 10 | 账号隔离 | localStorage 按 origin 共享，未按司机账号隔离；切换账号需清理队列 |
| 11 | 设备时钟 | `capturedAt` 取设备时间，时钟不准会影响轨迹排序；生产需服务端校正 |
| 12 | 真实后端与鉴权 | 本卡只有 mock；没有 Telegram initData 校验、限流、鉴权与真实存储 |
