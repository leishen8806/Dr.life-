## 0. 一句话结论

**第一版用 PostgreSQL 够用，不需要上 Meilisearch / OpenSearch**，但必须用
**「pg_trgm 粗筛 + 字符 bigram 精排 + 同义词/拉丁转写表」的两段式方案（方案 F）**，
而不是任务表最初设想的「全文检索 + pg_trgm + 同义词」直接拼。

实测：50 条查询 **召回率 0.960、首位命中率 0.960**；10 万商品下 **p95 = 17.45 ms**、
三个 GIN 索引合计 44 MB。

**最重要的反直觉发现：PostgreSQL 内置全文检索（`to_tsvector`）对高棉语基本无效**
（召回率 0.327，比朴素 `ILIKE` 的 0.540 还差）。原因见 §3.1。
任务表原文写的「PostgreSQL 全文检索 + pg_trgm + 同义词表」里，**全文检索这一项应当去掉**。

## 3. 关键发现

### 3.1 内置全文检索对高棉语和中文**不可用**（最重要）

高棉语**词间不加空格**，中文同理。`to_tsvector('simple')` 按非字母数字边界切词，
于是**整条商品名变成一个巨型 token**。实测证据：

```sql
select id, tsv from poc.doc where id = 11;
```
```
 id |                      tsv
----+------------------------------------------------
 11 | 'electric':2 'fan':3 'កង្ហារអគ្គិសនី':4 '电风扇':1
```

`កង្ហារអគ្គិសនី`（电风扇）整体是 **1 个** token，`电风扇` 也是 **1 个** token。
后果：只要用户不是一字不差地打出整个词，全文检索就完全命中不到 ——
`km-partial` 召回率 **0.069**、`zh-partial` **0.000**。

> **对《技术方案与系统边界》的修订建议**：PoC 清单第 4 项「高棉语搜索」的结论，
> 以及搜索章节「第一版用数据库全文检索即可」的说法需要改。
> 准确说法是「**第一版用数据库够用，但必须走 pg_trgm + 字符 n-gram，不能用 tsvector 全文检索**」。
> 要用 tsvector 就必须先引入高棉语分词器（ICU / 外部分词服务），成本远高于方案 F。

### 3.2 高棉语拼写变体只有字符 n-gram 扛得住

`km-variant` 是本 PoC 的核心难点，也是最能区分方案的一类：
`ilike` 和 `fts` 都是 **0.000**，pg_trgm 只有 **0.500**，字符 bigram 是 **1.000**。

原因是 bigram 对「少打一个符号」优雅降级。实测：

```
 grams_correct | grams_typo | shared
---------------+------------+--------
             7 |          6 |      5     -- ទូរស័ព្ទ vs ទូរសព្ទ（漏写 ័）
```

8 个变体查询覆盖的真实高棉语现象：

| 查询 | 正确写法 | 现象 |
| --- | --- | --- |
| `ទូរសព្ទ` | `ទូរស័ព្ទ` | 漏写 `័`（极常见） |
| `សាបូកក់សក់` | `សាប៊ូកក់សក់` | 漏写 `៊` |
| `នាលិកាឆ្លាតវៃ` | `នាឡិកាឆ្លាតវៃ` | 辅音混淆 `ឡ`→`ល` |
| `ក្រីមការពារកំដៅថ្ងៃ` | `ក្រែម…` | 元音混淆 `ែ`→`ី` |
| `ស្បែកជើងកិឡា` | `…កីឡា` | 元音混淆 `ី`→`ិ` |
| `ទឹកដោះគោមសៅ` | `…ម្សៅ` | 漏写下标符 `្` |
| `ធុងសរាម` | `ធុងសំរាម` | 漏写 `ំ` |
| `កាហេ្វបំពង` | `កាហ្វេបំពង` | **下标辅音与元音顺序颠倒**（真实编码变体） |

### 3.3 拉丁转写查询：任何纯匹配方案都是 0，只能靠词表

柬埔寨用户大量在没有高棉文键盘的情况下直接打拉丁字母。`km-romanized` 这一类
在 `ilike`/`fts`/`trgm`/`bigram` 下**全部是 0.000** —— 因为查询与商品名**没有任何共同字符**。
唯一解是**拉丁转写 → 高棉文的映射表**（本 PoC 放在 `poc.synonym` 里），加上后变成 **1.000**。

> 这是一个**产品级结论**，不只是技术细节：
> 搜索上线必须配一张转写词表，并且需要**母语者持续维护**（见 §1 警告）。
> 建议从真实搜索日志里挖零结果查询来增量补充。

### 3.4 中文同音错别字：字符 n-gram **结构性**无解

这是推荐方案唯一的明确短板，我不藏：

```
   q    | correct | typo_grams  | correct_grams | shared_bigrams
--------+---------+-------------+---------------+----------------
 电风善 | 电风扇  | {电风,风善} | {电风,风扇}   |              1
 牙高   | 牙膏    | {牙高}      | {牙膏}        |              0
 雨散   | 雨伞    | {雨散}      | {雨伞}        |              0
```

两字词的同音错字与正确写法**共享 0 个 bigram**，所以**调任何阈值都救不回来**
（三字词 `电风善` 共享 1 个，降到 0.5 阈值可救，这也是 `zh-typo` 能到 0.333 的原因）。

正解是**拼音**（`diàn fēng shàn` ≈ `diàn fēng shàn`），不是字符 n-gram。
建议：**第一版不做中文纠错**。理由——买家端是柬埔寨本地用户，主用高棉语/英语；
中文主要出现在商家端与平台后台，那里用户知道自己卖什么，错别字搜索不是主场景。
若后续要做，加一列拼音并对拼音做 bigram 即可，不影响现有架构。

### 3.5 单字查询必须有子串兜底

纯 bigram 对单字查询（如 `洗`）**必然 0 召回**：查询 bigram 是 `{洗}`，
文档 bigram 是 `{洗衣, 衣机, …}`，两者永不相交。这是 n-gram 的结构性缺陷，不是阈值问题。
所以方案 E/F 都保留了**精确子串层并让它永远优先**。

### 3.6 性能陷阱：`word_similarity()` 函数写法不走索引

这个坑我踩了并实测确认，**实现时必须注意**：

```
---- q <% body（运算符）----
 Bitmap Heap Scan on doc_scale d (actual rows=7000 loops=1)
   ->  Bitmap Index Scan on idx_scale_trgm (actual rows=7000 loops=1)
         Index Cond: (body %> 'សាប៊ូ'::text)

---- word_similarity(q, body) >= 0.3（函数，反例）----
 Seq Scan on doc_scale d (actual rows=7000 loops=1)
   Filter: (word_similarity('សាប៊ូ'::text, body) >= '0.3'::double precision)
   Rows Removed by Filter: 93000
```

必须用 `<%` 运算符 + `pg_trgm.word_similarity_threshold` GUC。
写成 `word_similarity(...) >= x` 会退化成全表扫描 —— 修这一处就让 p95 从 492 ms 降到 17 ms。

另一个好消息：`gin_trgm_ops` **也能加速 `LIKE '%…%'`**，所以精确子串层同样可索引：

```
 Bitmap Heap Scan on doc_scale d (actual rows=5000 loops=1)
   Recheck Cond: (body ~~ '%សាប៊ូ%'::text)
   ->  Bitmap Index Scan on idx_scale_trgm
         Index Cond: (body ~~ '%សាប៊ូ%'::text)
```

## 4. 索引大小与查询延迟（10 万商品实测）

100 个商品的索引只有几十 kB、查询亚毫秒，**那个量级对生产选型没有参考价值**。
所以准确率用 100 个标注商品评测，**性能另在 10 万商品上实测**
（由 100 个真实商品名 × 1000 组三语规格/品牌修饰词交叉生成）。

### 索引大小

| 对象 | 大小 | 建索引耗时 |
| --- | --- | --- |
| `doc_scale` 表（10 万行） | 80 MB | 建表 34.6 s |
| GIN on `tsvector` | 11 MB | 290 ms |
| GIN on `text[]` bigram（`array_ops`） | 14 MB | 1 518 ms |
| GIN on `body` (`gin_trgm_ops`) | 19 MB | 1 264 ms |
| **三索引合计** | **44 MB** | — |

索引大小完全不是瓶颈（合计 44 MB vs 表 80 MB）。
注意 bigram 物化列的**写入成本**偏高：10 万行算 bigram 用了 34.6 s（约 0.35 ms/行），
生产上应作为生成列/触发器在写入时增量计算，不要全表重算。

### 查询延迟（全部 50 条查询，毫秒）

| 方案 | avg | p50 | **p95** | max |
| --- | --- | --- | --- | --- |
| B `fts`（内置全文检索） | 0.88 | 0.28 | 4.42 | 9.39 |
| C `bigram`（纯 SQL，无扩展） | 157.78 | 106.49 | **689.88** | 718.83 |
| D2 `trgm_word`（pg_trgm） | 16.30 | 11.12 | 56.33 | 103.62 |
| **F `rerank` cand=100（推荐）** | **6.33** | **4.22** | **17.45** | 38.51 |
| F `rerank` cand=300 | 22.17 | 17.09 | 55.10 | 83.74 |
| F `rerank` cand=1000 | 77.73 | 68.36 | 148.67 | 211.92 |

**纯 SQL bigram（方案 C）虽然准确率高，但不能上生产**：p95 690 ms，
且 10k→100k 时 p95 从 70 ms 线性恶化到 690 ms。
根因实测：`&&` 粗筛会返回最多 **64 000 / 100 000** 行候选，再在 SQL 里逐行算 coverage。

| 查询 | 候选行数（10 万中） |
| --- | --- |
| `electric fan` | 64 000 |
| `ឆ័ត្រ`（雨伞） | 56 800 |
| `ម៉ាស៊ីន`（机器，词根） | 25 300 |

方案 F 正是针对这个瓶颈：第 1 段用 pg_trgm GIN 索引把候选压到 100 条（C 实现，走索引），
第 2 段只对这 100 条算 bigram coverage。**准确率拿到 bigram 的 0.960，延迟拿到 17 ms。**

## 5. 推荐方案（方案 F）

```
用户查询
  │
  ├─ 规范化：去零宽字符(U+200B/C/D, NBSP, BOM) → 高棉语数字 ០-៩ 折叠 → 小写 → 压空白
  │
  ├─ 同义词 / 拉丁转写展开（sabou → សាប៊ូ，fridge → refrigerator）
  │
  ├─ 第 0 层：精确子串 LIKE '%q%'（走 gin_trgm_ops 索引）── 永远排最前
  │
  ├─ 第 1 段：pg_trgm 粗筛  q <% body，阈值放低到 0.3，取 top 100 候选
  │           （必须用 <% 运算符，不能用 word_similarity() 函数 —— 见 §3.6）
  │
  └─ 第 2 段：只对候选集算字符 bigram coverage，>= 0.5 保留，按 coverage 排序
```

检索文档 = 中文名 + 英文名 + 高棉语名 拼接 → **三语互搜天然成立**。

推荐参数（由 §6 敏感性分析得出）：`cand=100`、`trgm_floor=0.3`、`min_coverage=0.5`。

### 为什么不上 Meilisearch / OpenSearch（第一版）

1. **准确率已经够**：0.960 / 0.960，唯一短板是中文同音错别字，而那不是第一版的主场景（§3.4）。
2. **延迟够**：p95 17 ms @ 10 万商品，远低于交互搜索可感知阈值。
3. **架构成本**：专用搜索引擎要引入新服务、索引同步、一致性与运维负担；
   而 Dr.life+ 第一版是托管机柜自建（架构文档第六章），多一个有状态服务代价明显。
4. **扩展已批准且随镜像自带**，不增加部署复杂度。

**什么时候该重新评估**（给出可检验的触发条件，而不是「以后再说」）：

- 商品数超过 **50 万**，或 `rerank` p95 超过 **100 ms**；
- 需要中文/高棉语**真正的分词与词形归一**（而非字符近似）；
- 需要个性化排序、向量语义检索、或复杂聚合分面；
- 搜索 QPS 高到 bigram 物化列的写放大影响正常下单写入。

## 6. coverage 阈值敏感性

只报一个阈值下的漂亮数字是不负责任的。`avg_returned` 作为噪声代理指标
（阈值越低召回越高，但返回的无关商品越多）：

| min_coverage | 召回率 | 首位命中率 | 平均返回条数 |
| --- | --- | --- | --- |
| 0.3 | 0.960 | 0.960 | 3.34 |
| 0.4 | 0.960 | 0.960 | 2.86 |
| **0.5** | **0.960** | **0.960** | **2.40** |
| 0.6 | 0.940 | 0.940 | 1.70 |
| 0.7 | 0.920 | 0.920 | 1.58 |
| 0.8 | 0.920 | 0.920 | 1.52 |
| 1.0 | 0.660 | 0.660 | 1.24 |

**0.5 是拐点**：召回率到顶（0.960），同时返回条数最少（2.40）。低于 0.5 只增噪声不增召回。

## 7. 真实高棉语查询样例（实际返回）

## 8. 已知风险与未证实项

**已知风险**

1. **高棉语译名未经母语者复核**：34/100 条标为 `needs-native-review`，
   拉丁转写表同样需要母语者扩充。**这是上线前的硬阻塞项**，不是可选优化。
2. **中文同音错别字无解**（§3.4），结构性限制，需要拼音方案才能解决。
3. **码位 n-gram 而非字素簇 n-gram**：当前按 Unicode 码位切 bigram，会把基辅音与
   其元音符号/下标辅音拆开。这正是能扛拼写变体的原因，但排序精度略有损失。
   改成高棉语字素簇 n-gram 可能进一步提升排序质量 —— **未证实，本 PoC 未实现对照**。
4. **bigram 物化列写放大**：10 万行重算 34.6 s（约 0.35 ms/行）。
   生产必须增量计算（生成列/触发器），批量导入商品时需评估影响。
5. **评测集规模有限**：50 条查询、单人标注（我本人）。
   类别覆盖是经过设计的，但不能替代真实搜索日志。上线后应用零结果查询持续校准。
6. **同义词表随规模增长**可能变成维护负担，且当前展开是查询期 `LIKE` 扫全表
   （24 条时无所谓，上千条需要给 `poc.synonym.term` 建索引）。

**未证实（本 PoC 未做，不下结论）**

- **ICU 分词**：镜像内有 ICU 76（`libicuuc.so.76`），但 PostgreSQL **不把 ICU 的
  词边界分析（word break）暴露成分词器**，只用于排序规则（collation）。
  要用 ICU 分词需要外部分词服务或自写扩展 —— **成本未评估，未实测**。
- **外部分词服务**（如 Khmer 专用分词微服务）：未实测延迟、准确率与运维成本。
- **Meilisearch / OpenSearch 实际表现**：未部署对照，§5 的「不上」是基于
  「方案 F 已满足需求 + 架构成本」推理，**不是**基于与它们的实测对比。
- **真实柬埔寨用户查询分布**：无线上日志，查询集由我按语言学现象构造。
- **并发表现**：所有延迟数据都是单连接顺序执行，**未做并发压测**。

## 10. 给 T-03 的落地建议

T-03（商品搜索接口）可以解锁，按以下约束实现：

1. **不要用 `to_tsvector` 做高棉语/中文检索**（§3.1）。
2. 迁移里需要 `CREATE EXTENSION pg_trgm`（属 F-03 迁移任务范围，**需另行评审**）。
3. 检索文档列 = 三语名拼接后规范化，建议生成列 + `gin_trgm_ops` 索引；
   bigram 列用 `text[]` + `gin (array_ops)`，**增量计算**。
4. 必须用 `<%` 运算符而非 `word_similarity()` 函数（§3.6）。
5. 同义词/拉丁转写表需要后台可维护（归属 `catalog` 模块自己的 schema，遵守模块边界）。
6. 排序按《技术方案与系统边界》要求叠加标准分与销量加权；
   广告位单独标注、不影响自然排序 —— 本 PoC 只解决**匹配与召回**，不含商业排序。
7. 搜索接口需记录零结果查询，用于增量补同义词表。

**本 PoC 未实现 T-03 的搜索接口，也未改 `catalog` 表结构**（任务卡要求）。
